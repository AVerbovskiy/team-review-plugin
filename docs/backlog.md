## To decide

### Move key team rules into `context/team-context.md`
_Added 2026-11-17._

**Today:** the team's rules reach the reviewers only through the **team brief**. The context builder writes it by
condensing the Confluence pages (Code Review, Definition of Ready) and the repositories listed in `team-context.md`.
That summary is generated by a model, so a rule can be shortened, merged with another one, or dropped without anyone
noticing. A rule that is not in the brief is a rule no role checks.

**Idea:** copy the rules that matter most in review directly into the **Working agreements** section of
`team-context.md`, written as short, checkable statements with their source, for example:

```markdown
- Code review agreement: every comment states whether it blocks the merge: **blocking**, **question**, **suggestion**, **nit**.
- Code review agreement: the PR description states the intent, how to verify, and what to scrutinise.
- DoR (Story): the ticket lists Scope (included / excluded), Edge cases and Testing.
- Every Kafka consumer is idempotent on the event ID. (team convention, not yet written down)
```

Rules in `team-context.md` reach every reviewer **verbatim** and are versioned with the skill. The Confluence pages
stay as the source of background and reasoning.

**Questions to answer:**
- Which rules are important enough to copy? A suggested filter: rules a reviewer can check against code or the PR,
  and that we have seen broken.
- Who keeps the copy in sync when a Confluence page changes? (owner, and how often)
- Should repo-specific rules live in each repo's `.claude/team-review.md` instead, with only team-wide ones here?
- First, after a few reviews, read `~/.cache/team-review/team-brief.md` and check what the generated brief keeps and
  what it loses. That shows which rules need copying.

### Per-user model overrides
_Added 2026-11-17._

`config.json` lives inside the skill folder. Once the skill is a plugin, an update overwrites that folder, so a person's
own model choices would be lost. Decide whether to read an optional user file (for example
`~/.config/team-review/config.json`) on top of the shipped defaults, and whether a repo may set models in
`.claude/team-review.md`.

### Judge model
_Added 2026-11-17._

With Sonnet, the judge rejected nothing and merged no duplicates, where Opus had rejected 5 (4 duplicates). Compare a
Sonnet and an Opus judge on the same saved findings before deciding the default.

### Related code: tune the search
_Added 2026-11-17._

`related_code.json` is a plain text search, so it lists irrelevant files too (25 on one PR). Watch whether that noise
costs tokens or attention, and tune it if needed: rank terms from the lines that change a rule (conditions, failure
reasons) above plain names, or cap the list lower.

### Other ideas from the first review of the skill
_Added 2026-11-17._

- **Repo config for a service repository:** add `.claude/team-review.md` with the project rules
  (domain invariants, ADR path).
- **`--show-rejected`:** show the findings the judge rejected and why, to see which roles produce noise and tune them.
- **`lang=bg` when posting:** if comments on GitHub are always in English, remove it. It is the most fragile part of
  posting (the translation is written into `review.json` on the fly).
- **`questions` keyword** in `/team-review:post`: probably unused; `blockers` and `majors` may be enough.
- **`--suggestion` on by default** when a finding has an exact replacement, with a flag to turn it off.
- **Remove stack detection** from `collect.py`: the stack is set in `team-context.md` and agents can see `package.json`.
- **Plugin:** move the three skills and the two agents into a team plugin in a git repo (`claude plugin install …`), with automatic updates.
